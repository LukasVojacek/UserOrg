Waldur Sync Refactor

Event-producing sync module for the Waldur integration

A junior-friendly guide to the approved architecture and decisions

Approved 2026-07-06 Amended after independent review

What We Are Building

Replace the current Waldur integration (Waldur.EFP, Waldur.Puhuri, WaldurPlatform.Base, ~5 000 LOC across multiple projects with complex channel pipelines) with a new, simple, long-term-maintainable implementation that keeps all the functionality but restructures it along a clear boundary.

The new shape has three parts:

  • Waldur.Contracts — Integration event types + IWaldurEventPublisher port (the seam)
  • Waldur.Sync — Pull module: per-instance sequential worker, SHA change detection, event emission
  • Consumer handlers in Userorg.Adapter/Waldur — Small handlers, one per event type, apply events to the UserOrg database

Still a monolith today, but the seam is exactly where RabbitMQ slots in later: swap the in-process publisher for a queue publisher, host the handlers behind a queue consumer, lift Waldur.Sync into its own container. Nothing else changes.

Why this shape: The one boundary that matters is "pull side produces events, UserOrg side consumes them". Everything inside either side stays as plain, sequential, readable code. We deliberately do NOT rebuild the current channel pipeline — it solved a throughput problem the 30-minute cadence doesn't have, at the cost of making "which item failed and why" nearly unanswerable.

Target Architecture & Iteration Algorithm

                 Waldur API (per instance: EFP, Puhuri, …)
                          │  HTTP pull (30 min) — future: push trigger joins here
                          ▼
┌─ Waldur.Sync ────────────────────────────────────────────────────────┐
│  per enabled instance (config Waldur:Instances):                     │
│    WaldurApiClient  →  payload mapping  →  SHA diff  →  events       │
│    + storage-config hash → StorageConfigurationChanged (ADR-0061)    │
│    (sequential worker; SHA map in memory, cold rebuilt on start)     │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ IWaldurEventPublisher (Waldur.Contracts)
                               ▼         ← the future RabbitMQ seam
┌─ Userorg.Adapter/Waldur (consumer) ──────────────────────────────────┐
│  InProcessWaldurEventPublisher → handler per event type              │
│  (own DI scope per event, direct IUserOrgDbContext, Heappe in        │
│   ProjectUpsertHandler for both Created AND Updated, one event =     │
│   one SaveChangesAsync)                                              │
└──────────────────────────────────────────────────────────────────────┘

Per-iteration algorithm (one instance):
0. Startup only: cold rebuild SHA map from DB; publish one StorageConfigurationChanged.
1. Storage config: hash config; if ≠ map → publish StorageConfigurationChanged; SHA update only after ack.
2. Providers: fetch customers; per customer fetch offerings; derive locations (ADR-0054/A3) → map to ProviderPayload → hash → Created/Updated or skip.
3. Projects: fetch all projects; per project fetch resources + offering details (bounded concurrency) → apply eligibility rules (ADR-0054/A4) → map with IsRemoved flag → hash → Created/Updated or skip.
4. Users: per eligible project fetch list_users (complete snapshot or explicit failure — D7). On success: diff per (projectExternalId, userName) → UserAssigned/UserRoleChanged/UserRemoved. On failure: warning, skip membership this iteration.
5. Each event: successful PublishAsync → write SHA entry. Failure → structured error, no SHA write, continue. Absence transitions → warning (ADR-0058/A1).
6. End of iteration: always-log summary; sleep delay measured from completion (ADR-0056/A2).

Architecture Decision Records (9 ADRs)

One card per ADR. Cards for amended ADRs present the amended state as the truth. ADR-0060 (optional Phase 6) is marked with a dashed border and lighter background.

Rewrite as Event-Producing Module
ADR-0053
The Problem
The current integration is ~5 000 LOC split across four projects with complex channel pipelines (1–32 worker pool, drain phases, dead-letter queue) and fragmented logic making "which item failed and why" hard to answer.
The Choice
Create three new projects with a clear boundary: Waldur.Contracts (event types + port), Waldur.Sync (pull side, sequential worker), and consumer handlers in Userorg.Adapter/Waldur. Instances (EFP, Puhuri) are configuration, not code. STOMP listener not ported.
Key Consequence
  • Old projects deleted in the same branch → one cutover.
  • Future RabbitMQ move = swap publisher + host handlers behind queue consumer; all core code stays byte-identical.
  • Platform differences live in options and payload content only, no parallel class hierarchies.
For Junior Devs
You are building three small, focused projects instead of one complex pipeline. The pull side produces events. The write side consumes them. The seam between them (IWaldurEventPublisher) is where RabbitMQ will go later.
Fat CRUD Events
ADR-0054 (AMENDED)
The Problem
Thin notification events ("id changed, fetch it back") create request/reply loops and re-couple pull and write sides. Deletion hazards: false ProjectDeleted on paging bugs would be the most damaging failure of the whole integration.
The Choice (Amended)
  • Events carry full payload (event-carried state transfer); consumer never calls back.
  • Removal is an IsRemoved flag in ProjectPayload, not a separate ProjectDeleted event. Waldur's is_removed maps to this flag, included in hash.
  • Resources travel inside project events (no independent lifecycle).
  • Membership is diffed per user; membership identity is UserName, not Waldur UUID (UUID not stored; cold rebuild impossible).
  • Provider locations are derived from offerings and embedded in ProviderPayload (not raw API data).
  • Eligibility rules are part of the contract: resource needs allocations + EffectiveId/BackendId; project needs ≥1 eligible resource OR IsRemoved=true; ineligible projects emit no events (including membership).
  • UserRemoved only from a successfully fetched, complete member snapshot; failed fetch → no membership events for that project.
Key Consequence
Consumers are idempotent by construction (upsert semantics). Removal in Waldur is just another ProjectUpdated; no delete/create ping-pong. Producer must diff member lists per user.
For Junior Devs
When you map Waldur data to events, include everything the handler needs to write. No calling back. If Waldur says "removed", write an IsRemoved=true flag, not a delete. If a user isn't in the fetch, that's a real removal only if the fetch succeeded completely.
SHA Breadcrumb Map with Cold Rebuild
ADR-0055 (AMENDED)
The Problem
Today every 30-min iteration re-upserts everything — no change detection, wasted DB writes, log floods. Diff state must not drift from the database, and must survive moving Waldur.Sync to its own container.
The Choice (Amended)
  • In-memory map per instance: (instance, entityType, externalId[, userName]) → SHA-256.
  • SHA computed from canonically serialized event payload (normalized DTO, not raw API).
  • No persistence. Cold rebuild on startup: DB → DTO (same shape as API mapping) → hash. First iteration more expensive; acceptable at 30-min cadence.
  • Normalization checklist (binding): (A1) No clock reads; (A2) truncation to DB limits in producer mapping; (A3) canonical GUID format (lowercase "D"); (A4) UTC, defined precision; (A5) null-date conventions; (A6) null=empty collections, sorted; (A7) strings trimmed, endpoint-normalized; (A8) decimals invariant-culture; (A9) derived values reproducible from DB.
  • Shared entities (users): hash only instance-owned fields (project, userName, role, access); profile fields create-only, not hashed (ADR-0055/A3).
  • Reconciliation-owned rows excluded: Any AssignedLocation/Location with ServiceName=EfpCoreServiceName never enters a payload or hash (ADR-0061).
  • Soft-deleted projects included in cold rebuild (IsRemoved is hashed).
  • Storage config never cold-rebuilt; worker always fires one StorageConfigurationChanged after startup.
Key Consequence
Unchanged items produce zero events, zero DB writes, zero log lines. Round-trip hash test (Phase 4.8) guards that API→DTO and DB→DTO produce identical hashes — the core invariant.
For Junior Devs
Your mapping function must be deterministic and idempotent. If it reads the clock, exclude that field from the hash. If the API sends GUIDs without dashes, normalize them in one place. Write truncation in mapping, not at save time. Test that reading the same item from Waldur API vs. the database produces the same hash.
Sequential Worker, Synchronous Ack
ADR-0056
The Problem
Complex channel pipeline (worker pool, drain phases, DLQ) makes failure attribution hard. If SHA is updated before the handler finishes and then fails, the change is lost forever.
The Choice (Amended)
  • One sequential worker per instance. Plain loop: fetch → build DTO → diff → publish → continue. Parallelism allowed only where API latency demands it (bounded, not architectural).
  • Synchronous ack. PublishAsync completes only after the handler (DB write, Heappe init) completed. SHA written only on success. Failure → no SHA write → retry next iteration.
  • No DLQ. Retry is free from the pull loop. Permanent failures show as repeating structured errors (monitoring signal).
  • Missing parent = throw, never skip-and-ack (ADR-0056/A1). A ProjectCreated whose provider failed will fail in the handler → no ack → retry next iteration.
  • Timer measured from completion (ADR-0056/A2): sleep interval after iteration finishes, so overlap is impossible by construction.
  • Unique-constraint races on shared reference data are retriable failures (ADR-0056/A3). SQL 2601/2627 on concurrent get-or-creates is natural; next iteration wins by reading the existing row.
  • Fetch completeness explicit (ADR-0056/A4): API client throws on any page failure (old code silently truncated). Bounded concurrency for per-project detail fan-out.
Key Consequence
Failure attribution is trivial: one stack, one item, one log scope. Consumers must be idempotent (they are — upsert semantics). On RabbitMQ move, ack semantics shift (SHA on broker confirm, consumer retry); idempotence from day one makes that safe.
For Junior Devs
Write a for-loop iteration, not async pipelines. When something fails, log it with the item's ID and what phase it failed in (fetch, map, diff, publish, handler, heappe). Throw if you can't resolve a parent; don't log-and-ack. Let the loop retry.
Handlers, Direct DbContext, Heappe in Upsert
ADR-0057 (AMENDED)
The Problem
Today ~2 900 LOC of exporters (WaldurEfpExporter, PuhuriExporter) + extensions duplicate orchestration. They differ only in data, not behaviour. Heappe placement undefined.
The Choice (Amended)
  • Small handlers, one per event type, shared by all instances (EFP/Puhuri differences in payload, not code).
  • Direct IUserOrgDbContext. No repo/port layer between handlers and DbContext.
  • One DI scope per event. Fresh DbContext, so concurrent workers can't share EF state.
  • Heappe runs in the ProjectUpsertHandler (Created AND Updated), per HPC resource (ADR-0057/A1). Not ProjectCreated alone — resources added to existing projects must be initialized. Heappe is get-or-create-or-update (idempotent); replay is safe.
  • Heappe command-template sync trigger per upserted HPC resource (ADR-0057/A2).
  • Atomicity: mutate tracker → external ensures (Heappe) → single terminal SaveChangesAsync (ADR-0057/A3). Heappe failure → exception → nothing committed → retry next iteration. No manual transactions (retrying strategy forbids bare BeginTransactionAsync).
  • Membership handlers cover five row kinds per member (ADR-0057/A4): User (create-only profile), AssignedUserToProject, UserPermission (role map), PlatformUser permission, UserProjectAccess.
  • Service account bootstrapped by consumer (ADR-0057/A5, D18): idempotent EnsureServiceAccountAsync per instance, the CreatedBy/AssignedBy identity for all writes.
Key Consequence
~2 900 LOC replaced by a handful of readable handlers. Ported behaviours (validation, upsert keys, role assignment, enrichment) re-expressed as tests first, then implementation. Partial handler success before exception tolerated by design (replay + idempotence).
For Junior Devs
Write one handler per event type. Mutate the change tracker, call Heappe, then SaveChangesAsync once. If something fails, throw — the event won't be acked and will retry. Your handler is called as many times as it takes, so make it safe to replay (idempotent).
Logging Contract (StepUpLogging Levels)
ADR-0058
The Problem
Today 488 lines of log messages across two LogMessages.cs files, including per-item logging of unchanged items. Hard to find signal in the noise.
The Choice (Amended)
  • Debug: Payload summaries, SHA old/new comparison, per-event emission.
  • Information: Start/end of processing each Waldur entity. Normally suppressed; surfaces via step-up around failures, giving exact context.
  • Information (always-log): Iteration summary (2 lines per instance per iteration): start (instance, trigger) and result (duration, fetched, created, updated, removed, unchanged, failed, absent transitions, blocked-by-parent).
  • Warning / Error: One structured entry per failed item: instance, entityType, externalId, phase (fetch|diff|publish|handler|heappe), reason, outcome (retry next iteration).
  • Absence warns only on transition (ADR-0058/A1): item was in map, not in successful pull → transition warning. Ongoing absences appear as count in iteration summary. Prevents false step-ups on legitimately unserved projects.
  • Cascade error aggregation (ADR-0058/A2): failed parent cascades into N child errors per iteration by design. Summary counts them separately (failed: N (M blocked-by-parent)) so root cause doesn't read as N independent problems.
  • Unchanged items produce no log line at any level. Zero changes, zero failures → exactly two always-log lines per iteration.
Key Consequence
~15 message definitions replace 488 lines. Permanently failing items visible as repeating errors with stable IDs (monitoring hook). Log volume scales with change volume and failures, not data volume.
For Junior Devs
Log Info when processing starts/ends. Log Warning/Error when something fails, with the item's ID. Use structured fields (instance, phase, externalId). Let step-up logging surface the context. Don't log unchanged items.
Cutover & Acceptance: Parallel Run
ADR-0059
The Problem
Keeping two implementations side by side in the repo costs duplicate code and tests. Parallel enablement risks corrupting production.
The Choice (Amended)
  • Replace in one feature branch. New Waldur.Contracts + Waldur.Sync + consumer handlers built; old projects deleted in the same branch. Merge = cutover (no window where both coexist on main).
  • Acceptance gate before deletion: both implementations run against their own empty UserOrg database with the same test Waldur instance; data compared using specified methodology (ADR-0059/A1).
  • Comparison methodology (ADR-0059/A1): project to natural-key projections (FKs joined through to external ids/names), explicit exclusion list (surrogate ids, CreatedAt, ModifiedAt, audit users), pre-approved expected-differences list (per-user vs. all-or-nothing membership transactions, manual-member sweep timing, eliminated no-ops, per-resource vs. per-project partial progress, removed projects now reaching DB).
  • Isolate Heappe: stub or sandbox HEAppE per run (both against live Heappe = double external side effects).
  • Run old side one instance at a time (old DI singletons never actually supported concurrent instances).
  • Puhuri baseline by intent (ADR-0059/A2): today's Puhuri is broken (writes EFP service names, user export can never succeed). Acceptance compares against intended semantics (service name = instance name, own service account, no storage reconciliation); equivalence only meaningful for EFP.
  • Non-empty-DB data check (ADR-0059/A3, D17): because of A2, existing rows may carry wrong ServiceNames. Count mismatches; if hits exist, one-time data fix required before enabling.
  • First-run storm expected (ADR-0059/A4): mapping nuances (truncation, normalization) may emit a one-time wave of ProjectUpdated. With idempotent Heappe ensure, this is noise, not damage.
Key Consequence
No dual maintenance window. Comparison script is the definitive functional-parity check and should be scripted/repeatable. Rollback strategy is git revert, not a runtime toggle.
For Junior Devs
Write a test script that can run the old system and the new system side by side, then compare the databases. Know what differences are intentional (no-op writes eliminated, different transaction scopes). Be ready for a first-run storm of updates; that's OK if they're idempotent replays.
Optional Phase 6: Container Split over HTTP OPTIONAL
ADR-0060 (DEFERRED)
The Problem
We are not committed to keeping the pull side in the monolith right now. If we decide to detach it later (without RabbitMQ), the split should be a composition change only, not a rewrite.
The Choice (If/When Taken)
  • Core code stays byte-identical. Waldur.Contracts, Waldur.Sync internals, all handlers unchanged.
  • New host Waldur.Sync.Host (minimal worker host, ServiceDefaults/OTel); registers AddWaldurSync(...). Waldur:Instances config moves here.
  • HttpWaldurEventPublisher: POSTs serialized event to /internal/waldur-sync/events on userorg-api. API dispatches to the same handlers, returns 200 only after handler completes. HTTP response = ack → ADR-0056 semantics hold unchanged. Non-2xx or timeout = not acked. No automatic retries (ADR-0060/A1 — pull loop is the retry; Heappe makes handlers slow; retries race with already-running handler).
  • HttpShaMapRebuilder: startup calls GET /internal/waldur-sync/state?instance=… returning (entityType, externalId, userId?, sha). API-side computes hashes (DB → DTO → hasher), reusing same hasher from Waldur.Contracts → one implementation, round-trip guarantee intact.
  • Endpoints internal service-to-service only (/internal/waldur-sync/*; authenticated with API key or mTLS; rate-irrelevant).
  • Discipline adopted now: event payloads JSON-serializable, evolve additively only (cheap in monolith, mandatory after split).
  • Path to RabbitMQ: swap publisher for queue publisher, host handlers behind queue consumer. State endpoint stays HTTP.
Key Consequence
Monolith↔container decision becomes deployment choice, reversible: ~1 day of two adapter classes + one host + Aspire wiring. No core changes. Slight duplication of deployment surface (one more image/resource).
For Junior Devs (If Implemented Later)
You are not building this now. But know it's possible: the pull side can move to its own container by swapping the publisher to HTTP and adding a rebuilder endpoint. Event payloads must be JSON-safe from day one (write them that way in Phase 0).
EFP Storage Reconciliation
ADR-0061
The Problem
~600 LOC of InitializeStorageLocations runs at the end of every iteration, driven by configuration + current DB state, not pulled Waldur data — no CRUD event triggers it. Also, reconciliation-owned rows hang off the same resources that SHA cold rebuild reads → risk of permanent spurious-Updated storms if included in hashing.
The Choice
  • Write-time association (per project): Attaching/deactivating storage AssignedLocations for a project's resources becomes part of ProjectUpsertHandler. When project event is processed, handler reconciles that project's storage locations against current config (from event payload/consumer-side options). New resources get associations at write time, not in a later sweep.
  • Config-triggered full reconcile (per instance): Worker hashes instance's storage config (IrodsInstancesMap, StagingAreaInstancesMap, UseSharedIrodsForAllEntities, allocation amounts), keeps it in SHA map under key (instance, EntityType.StorageConfig, "config"). Publishes StorageConfigurationChanged on first iteration after startup and whenever config hash differs from map. Handler performs full sweep: ensure EFP-Core provider + shared-iRODS location, ensure/deactivate per-provider locations, walk all instance resources and fix associations (including deactivation when mapping disappears from config). Ack semantics as any other event.
  • Hash-exclusion rule (guards ADR-0055): DB → ProjectPayload mapping excludes reconciliation-owned rows (ServiceName = EfpCoreServiceName). They never enter a payload or hash. Reconciliation subsystem sole owner of those rows.
  • Puhuri unaffected: no storage config → no event, no handler work.
Key Consequence
Config changes take effect within one iteration with change detection. Steady state uses write-time association; full sweep runs only on startup and config change. Old end-of-iteration failure (storage reconcile fails whole iteration) replaced by ordinary per-event failure (logged, retried next iteration).
For Junior Devs
When you upsert a project, also reconcile its storage locations against the config you have (from the event or from options). When the storage config hash changes, emit StorageConfigurationChanged so the full-sweep handler runs. Mark reconciliation-owned rows so they don't pollute the SHA hash.

Normalization Checklist (Binding for Phase 0)

Apply these rules when mapping API data to payloads and DB data to payloads. They live in one place: WaldurPayloadHasher and the mapping code it documents.

  1. No clock reads anywhere in payload mapping (rule ADR-0055/A1). Audit fields never hashed.
  2. Truncation to DB limits in producer mapping (Name → DbConstants.NameMaxLength, Description → 512, …) so payload equals what lands in DB.
  3. Canonical GUID format: lowercase "D" with dashes. Waldur API delivers dashless GUIDs; normalize at client boundary.
  4. UTC everywhere, defined precision. Round to seconds unless field demonstrably needs more. DB round-trip must not lose hashed precision.
  5. Null-date conventions preserved: EndDate ?? DateTime.MaxValue applied in mapping, not at write time.
  6. Null vs. empty collection are the same value. Collections sorted by defined key before serialization.
  7. Strings trimmed; endpoint normalization (ssh:// strip, case rules) in mapping.
  8. Decimals serialized invariant-culture, fixed format.
  9. Derived/aggregated values (resource Min/Max date grouping, provider location derivation per ADR-0054/A3) must be reproducible from DB rows.

Implementation Phases

Each phase ends green (build + tests) and is independently reviewable. TDD throughout.

Phase 0 — Contracts (Waldur.Contracts)
  • New classlib (does not exist today; no collision).

Risks & Mitigations

DB→DTO vs API→DTO drift → spurious events after restart
Round-trip hash test (Phase 4.8) with adversarial vectors, in CI; ADR-0055/A2 checklist is binding.
Clock-derived field sneaks into a hash → perpetual Updated storm
ADR-0055/A1 rule + hasher test asserting payload hash stability across time.
Payload misses a field an exporter silently used
Phase 0 enumerates by reading exporter usage; acceptance diff (Phase 5.6) catches the rest.
Heappe regression (resource added to existing project)
D8 amended: ensure runs on upsert per resource; pinned by test.
Storage config change has no effect
D14: write-time association + config-hash-triggered reconcile; behaviour matrix tests.
Stale membership after restart
D15: UserName-keyed map is DB-rebuildable; rebuild spec ADR-0055/A4.
Puhuri on non-empty DB duplicates rows
Phase 5.5 data check before enable (0059/A3).
Permanently failing item loops every iteration
By design (no DLQ); repeating structured error + blocked-by-parent aggregation is the monitoring hook.
Two instances racing on shared reference data
Unique violation = retriable failure; optional retry-once (0056/A3); DI scope per event.
Acceptance diff drowns in nondeterminism
0059/A1 methodology: natural keys, exclusion + expected-difference lists, Heappe isolation.
