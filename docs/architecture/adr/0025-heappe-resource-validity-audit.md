# ADR 0025 - HEAppE resource validity audit is a read-only, flag-gated module feature with streaming + detached-webhook delivery

- Date: 2026-06-25
- Status: accepted

## Decision

Add a **resource validity audit** to the **Heappe integration module** (`src/Modules/Integrations/Heappe/Features/ResourceValidityAudit/`). It cross-checks, for every currently-valid **Resource** exposed on a HEAppE instance, that the HEAppE **project record** for that resource exists and carries the **same validity period** userorg holds, and reports the mismatches. It never writes back to HEAppE — it is the read-only mirror of the existing `ProjectCreationService` write path.

Concrete shape:

- **One shared service** `IHeappeResourceAuditService.RunAuditAsync(CancellationToken) : IAsyncEnumerable<TargetAuditResult>`. It streams **one result per processed target** (status `Ok | Missing | ValidityMismatch | CheckFailed`). Both consumers below drive this one method.
- **Enumeration via a dedicated host-contract port, on the refactored read side.** The set of audit targets (resource name, owning project short-name for labelling, HEAppE URL, HEAppE identifier, start/end dates) is fetched through a **new, dedicated port `IHeappeAuditTargetProvider`** (`HostContracts`) — *not* an extra method on the legacy-backed `IUserorgService`. A separate port keeps this one modular-read concern off the legacy-flavoured interface (ISP) and gives the audit a small, mockable seam. It is implemented host-side by a **new `IDataQuery` + read DTO in the modular `Core.DataAccess`** (not the legacy Application/`ProjectRepository` path the `IUserorgService` methods use). The query runs over the modular Provider/Project entities (`Core.Domain.Provider.ProjectResource` / `AssignedLocation` / `AssignedLocationValue` / `Location`, joined to the owning `Project` for its short name): valid, non-deleted resources assigned at **HPC or Quantum** locations (`ELocationType.HPC = 1`, `Quantum = 7` — the same type filter `ProjectRepository`/`WaldurHeappeProjectInitializer` already use) whose assigned-location values contain a `HeappeUriKey`. The module never references any Core DbContext directly.
- **Resource↔Project is a genuine M:N**, so the provider emits one row per *(project, instance)*; the audit then **dedups by `(resourceName, heappeUri)`**, because the HEAppE project record is keyed by resource name (one per resource-at-instance regardless of how many userorg projects share the resource). Consequence: when a resource is shared across projects, a finding's project label names one owning project arbitrarily. Acceptable for v1 (the check is per-resource); listing all owners is a later refinement.
- **Per-target check** reuses `ICredentialsService` (credentials by HEAppE identifier) + `IHeappeService.GetProjectByResourceName`, then compares HEAppE `ProjectModel.StartDate/EndDate` to the resource's own dates at **whole-day UTC granularity**. Targets are **deduplicated** by `(resourceName, heappeUri)`.
- **Scheduled worker** (`BackgroundService`): waits a hardcoded **60 s** after startup (no health-check gate), then loops on a `PeriodicTimer` whose interval is **configurable, default 8 h**. Each cycle first checks the feature flag; when enabled and the run yields findings, it POSTs **one** MS Teams adaptive card (Power Automate *Workflows* envelope, `{ type: "message", attachments: [...] }`) grouping findings by instance. A clean run posts nothing.
- **Manual endpoint** (`POST /HeappeResourceAudit/run`, Admin-only) with `?delivery=stream|webhook` (default `stream`):
  - `stream`: returns the `IAsyncEnumerable<TargetAuditResult>` directly (streamed JSON array, one item per *processed* target incl. `Ok`), so bytes flow continuously and the YARP proxy does not cut a multi-minute run. No webhook post.
  - `webhook`: starts the run **detached** (a `Task` on the application-lifetime token, *not* the request token), returns **`202 Accepted`** immediately, and POSTs the findings-only card when done. Failures in the detached run are logged + counted only.
- **Configuration** is split: the on/off flag is `FeatureManagement:HeappeResourceAudit` (existing `Microsoft.FeatureManagement` convention), evaluated **at runtime** each cycle and on each request; the rest is an Options class bound to `Heappe:ResourceAudit` (`WebhookUrl`, `Interval`). `Interval` is range-validated at startup (`ValidateOnStart`); `WebhookUrl` is validated **at use** (in the webhook sender) rather than at startup, so the app still boots when the feature is off and no webhook is configured — the URL is only required at the moment we actually need to notify.
- **Both** the worker and the endpoint are gated by the flag. Because the existing `DisabledByFeatureFlagMetadata` is a *kill-switch* (disables when the flag is **on**), we add an inverted **`EnabledByFeatureFlagMetadata` + `.EnabledWhen(...)`** branch in `FeatureFlagMiddleware` (returns 404 when the flag is **off**, matching the no-leak convention).
- **Admin-only enforcement** is the **Gateway RBAC route→permission mapping** (consistent with all other Heappe/admin endpoints, which carry no inline role attribute). Adding the route to that mapping is a required companion step — without it the endpoint is open to any authenticated caller.

## Context

- HEAppE projects are provisioned **per Resource** (keyed by resource name) by `WaldurHeappeProjectInitializer` → `ProjectCreationService`, copying the resource's `StartDate`/`EndDate`. Nothing today re-checks that this state still holds, so silent drift (e.g. a validity change not propagated) goes unnoticed.
- The data needed to enumerate targets lives on the **legacy Core** entities (`AssignedLocation` → `ProjectResource`, with HEAppE URL/identifier in assigned-location values), while every HEAppE-calling dependency lives in the **Heappe module**. The module already has the `HostContracts/IUserorgService` seam for exactly this "ask the host for userorg data" need.
- A full run is sequential and can take **minutes**; the in-process **YARP** gateway can cut a long, silent response. The audit is also operationally interesting even when verification *fails* (an unreachable instance hides drift), so "could not check" must be a first-class outcome, not a swallowed exception.

## Considered options

- **Module feature + host-contract port (chosen).** All HEAppE dependencies are already in the module; the new `IUserorgService` method keeps it decoupled from any Core DbContext, matching ADR-0017's one-directional read seam. Cost: one more host-contract method and its host-side query.
- **Refactored `Core.DataAccess` read side for the new query (chosen)** over implementing it on the legacy Application/`ProjectRepository` path like the sibling `IUserorgService` methods do. Chosen per the repo's "prefer `src/Modules/Core/` for new functionality" rule and the migration goal of deleting legacy: a new read should not deepen reliance on the layer being retired. Cost: new read-side infrastructure (a query object, a read DTO, and the Resource→Project join) instead of copying the ready-made legacy `ProjectRepository` HEAppE-links query — the deliberately less-lazy choice, justified by direction-of-travel.
- **Put the audit in the legacy Core / adapter** where the EF entities live. Rejected: spreads HEAppE-calling logic outside the module that owns it, duplicating connection/credential/version handling.
- **Streaming `IAsyncEnumerable` for the manual run (chosen)** over (a) buffering the whole result then returning — reintroduces the multi-minute silent response the proxy kills; (b) SSE — purpose-built but adds event-framing ceremony for no consumer that needs typed progress yet. The `webhook` delivery mode exists precisely for environments where even streaming is cut, trading the synchronous result for an instant `202` + detached post.
- **Inverted feature-flag metadata (chosen)** over an inline `IFeatureManager` guard in the handler. Chosen deliberately for declarative, reusable gating consistent with the existing kill-switch mechanism; the inline guard was the lazier single-endpoint alternative.
- **Stateless runs (chosen)** over persisting results to dedup alerts across runs. Rejected persistence as premature: an unfixed finding simply reappears each cycle until the data is corrected; no schema, no migration, no "new vs seen" bookkeeping until that noise is actually a problem.

## Consequences

- **The audit reports, never repairs.** If it should ever start *fixing* drift, that is a new decision — it would converge with `ProjectCreationService` and lose its read-only safety.
- **`IUserorgService` grows a query** the host must implement; the module stays free of legacy-DbContext coupling.
- **Toggling is runtime, not deploy-time.** Flipping `FeatureManagement:HeappeResourceAudit` starts/stops scheduled posting and enables/disables the endpoint without a restart; the worker stays registered and idles when off.
- **Detached `webhook` runs surface failures only in logs + metrics** (the caller already has its `202`). This is the accepted cost of dodging the proxy timeout.
- **A pathologically slow single HEAppE call** (up to the ~120 s `HeappeClient` total timeout) can still exceed a low proxy idle timeout even when streaming, because no bytes flow *during one call*. Per-target streaming fixes long total silence, not one slow instance; a periodic keep-alive tick is the upgrade path if it ever bites.
- **The Gateway RBAC mapping is load-bearing — fail-closed.** The endpoint's "Admin-only" guarantee lives in the route→permission entry in `roleManagmentRBAC.json` (`perm:platformadmin`), the same mechanism every admin route uses. The gateway fails closed: a route with **no** mapping is denied to everyone (403, "no permission mapping for this endpoint"), so forgetting the entry makes the endpoint unusable rather than open. The seed only imports into an **empty** `EndpointMappings` table, so existing deployments need the entry applied via the Role Management admin API/UI (an operational step), not a restart.
